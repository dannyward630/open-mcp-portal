# Open MCP Portal v0.1.0

This is Open MCP Portal's first release. Open MCP Portal is a self-hosted portal for a company's [Model Context Protocol](https://modelcontextprotocol.io) servers. Teams register the MCP servers they run and publish them to a company catalog. They curate **gateways**: sets of tools, prompts and resources served at one MCP endpoint, `/mcp/{slug}`. People and agents connect Claude Code, other MCP clients or their own scripts to a gateway and see only what they may use, with every call checked, limited and recorded. It is one Go binary with an embedded web UI, backed by PostgreSQL 17. The full list of changes is in the [changelog](../../CHANGELOG.md).

v0.1.0 contains phases 1 to 7 of the [specification](../../SPEC.md) (migrations `00001` to `00013`):

- **Registry and catalog.** Teams register remote MCP servers (Streamable HTTP). The portal reads their tools, resources and prompts, notices when a definition changes and holds it for review, and checks health on a schedule. Static header values are stored encrypted. Platform admins approve servers into the company catalog, or let trusted teams publish their own.
- **Gateways.** Curated capabilities, granted to teams, people or SSO groups, served at `/mcp/{slug}` and re-checked on every request. Tools and prompts are exposed as `{server}__{name}`, resources as `omp://{server}/{uri}`. Every call to an MCP server carries a short-lived ES256 identity token (JWKS at `/.well-known/jwks.json`), so servers learn who is calling without ever seeing the caller's credential.
- **Sign-in for MCP clients.** An OAuth 2.1 authorization server for each gateway (PKCE, Client ID Metadata Documents, dynamic registration, per-person consent, rotating refresh tokens). Personal API keys (`omp_`) for scripts.
- **Service accounts.** Team service accounts with expiring keys (`omp_sa_`) for pipelines and agents, two active at a time for rotation.
- **Delegated credentials.** Auth providers (presets for GitHub, Google, Microsoft Entra ID, Atlassian, Slack and GitLab) let a tool act as the caller. Each person consents once, and their token is stored sealed, refreshed and revocable. Without consent, the call returns a consent link (JSON-RPC `-32042`).
- **Per-person OAuth to upstream servers.** MCP servers that are OAuth-protected themselves, such as GitHub's hosted MCP server, get each caller's own sign-in: discovery, dynamic registration or a manual client, step-up, refresh.
- **Governance and operations.** Rate limits shared by every replica, opt-in payload capture (redacted, truncated, sealed, with audited views), retention, hourly usage rollups and reports, an append-only audit log and call log, Prometheus metrics, `ENCRYPTION_KEY` and `API_KEY_PEPPER` rotation (`open-mcp-portal rotate-keys`), `doctor`, and an allowlist of internal networks that platform admins manage.
- **Deployment.** A distroless multi-arch image, a Docker demo, a Kustomize base with an example overlay, and a Gmail MCP server example (`examples/mail-mcp`).

## First release

There is no previous version, so every install of v0.1.0 is a first install. Open MCP Portal is development software: it has not run in production. [Known limitations](#known-limitations) lists what has and hasn't been tried.

**Requirements.**

| Dependency | Notes |
|---|---|
| PostgreSQL | 17. The only state; there is no worker, cache, queue or object storage. |
| OIDC provider | The only production sign-in method. Register `${APP_URL}/auth/callback` as the redirect URI. |
| TLS | `APP_URL` must be `https://` outside development; the portal refuses to start otherwise. |
| Kubernetes | Optional. The manifests are validated against the 1.34 schemas. |

To build from source you need Go 1.26 or later and Node 22 or later.

**Try it** (Docker only, development sign-in, no setup):

```sh
make demo        # portal + PostgreSQL + a fake MCP server on http://localhost:8090
make demo-down   # stop it and delete its data
```

Sign in as `admin`, register the fake MCP server as `http://127.0.0.1:8091/mcp`, build a gateway from its tools and connect a client to `http://localhost:8090/mcp/<slug>` with a personal API key. The demo builds the image locally and uses public example keys that the portal accepts only for a loopback `APP_URL`. Never expose it.

**Install.**

1. Take the image `ghcr.io/ncecere/open-mcp-portal:v0.1.0`, pinned by the digest in the [Image](#image) section above and verified as shown [below](#verifying-the-images).
2. Copy [`deploy/kubernetes/overlays/example`](../../deploy/kubernetes/overlays/example/kustomization.yaml) into your own repository and replace its `example.org` values. Pin the image by digest with a Kustomize `images:` entry (`newTag: v0.1.0` and `digest: sha256:<digest>`). The [deployment guide](../deploy.md) covers the base, the secrets, ingress timeouts, NetworkPolicies, upgrades and backups. Elsewhere, run `open-mcp-portal migrate` and then `serve` from the same image.
3. Create the secret `open-mcp-portal-runtime` with `DATABASE_URL`, `ENCRYPTION_KEY`, `API_KEY_PEPPER` and `OIDC_CLIENT_SECRET`. Generate your own `ENCRYPTION_KEY` and `API_KEY_PEPPER`, each 32 random bytes in base64, and never reuse the example values from `.env.example` (the portal refuses them off loopback):

   ```sh
   openssl rand -base64 32     # ENCRYPTION_KEY
   openssl rand -base64 32     # API_KEY_PEPPER (a different value)
   ```

   Keep both in your secrets store and with your backups. Without `ENCRYPTION_KEY`, stored header values, identity signing keys and people's provider tokens can't be decrypted; without `API_KEY_PEPPER`, every API key and connected app stops working. Rotate them with `ENCRYPTION_KEY_PREVIOUS` and `API_KEY_PEPPER_PREVIOUS`, never by just replacing them ([Key rotation](../deploy.md#key-rotation)).
4. Set `APP_URL`, `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `TRUSTED_PROXIES` and, for the first sign-in, `BOOTSTRAP_ADMIN_SUBJECT` (the OIDC `sub` that becomes platform admin). Run `open-mcp-portal doctor` to check the configuration, Postgres and the migration state.
5. Connect a client: [connecting clients](../connect-clients.md).

## Verification

What was run before this release:

- **Real clients.** Claude Code signed in to a gateway over OAuth (a trusted client, so no consent page) and called tools. pi signed in over OAuth with dynamic client registration through the consent page and called tools.
- **A real upstream server.** GitHub's hosted MCP server (`https://api.githubcopilot.com/mcp/`) was set up in `oauth` mode with a GitHub App as the manual client. Each person signed in with their own GitHub account, and six tools worked from pi: `get_me`, `search_repositories`, `list_issues`, `list_branches`, `get_file_contents` and `search_code`. Running this found and fixed five bugs, listed under "Fixes since Phase 7" in the changelog.
- **Tests.** Go unit and integration tests (one database per test, race detector), a route test and an authorization matrix over every OpenAPI operation, and the web UI's Vitest suite with accessibility checks.
- **Deployment.** The image's `migrate` and `serve` in production mode against a scratch database, `/healthz`, `/readyz`, `doctor` and SIGTERM draining; the demo discovering the fake server's capabilities; `make k8s-validate` (the Kustomize base and overlay rendered and checked with kubeconform).

## Known limitations

Not verified yet:

- **A real Google or Microsoft delegated-credentials provider.** Auth providers were run only against a fake OAuth provider (`make fake-oauth`, with the Gmail example's fake Gmail). The only real provider run end to end is GitHub, through per-person OAuth to GitHub's hosted MCP server (a GitHub App).
- **VS Code and Cursor.** Only their configuration snippets are documented ([connecting clients](../connect-clients.md)). Claude Code and pi are the clients that were run.
- **Kubernetes on a cluster.** The manifests were rendered and schema-validated, not applied to kind or a real cluster. There is no smoke test.
- **Provider-token redaction** in captured payloads has unit tests but no end-to-end test through a provider-backed server.

Product limits:

- **Remote servers only.** MCP servers must be reachable over Streamable HTTP; the portal does not host or run servers (no stdio).
- **Stateless gateway.** `/mcp/{slug}` answers `POST` only, with JSON responses buffered up to 1 MiB. There is no streaming relay and no server-pushed notifications (so no `notifications/elicitation/complete`, no `listChanged`), and resource subscriptions are not supported.
- **No sampling, elicitation or roots passthrough.** The endpoint is stateless, so a server's requests to the client for these are not relayed ([gateways](../phase3-gateways.md#runtime-mcpslug)). The consent link for delegated credentials is an error the caller retries, not an interactive prompt.
- **Resources** are exposed under `omp://{server}/{uri}`, and resource templates are rewritten to the same form.
- **Rate limits** are counted in PostgreSQL in fixed one-minute windows, shared by every replica; the counters are unlogged and can be lost after a crash or failover. There is no per-address limit on unauthenticated `/mcp` requests: front it with your ingress's limits.
- **No background refresh** of delegated or upstream tokens (they refresh on use), no credentials for service accounts on delegated or upstream-OAuth tools, and one account per provider per person.
- **Deployment gaps.** No Helm chart, no HorizontalPodAutoscaler, no in-cluster PostgreSQL, backup job or restore procedure, no dashboards or alert rules, no tracing.
- Development software: it has not run in production.

## Verifying the images

The image is `ghcr.io/ncecere/open-mcp-portal`, tagged `v0.1.0` and `latest`, for linux/amd64 and linux/arm64. Deploy by digest: the digest is in the GitHub Release, its `open-mcp-portal-v0.1.0.digest.txt` asset, and the workflow's job summary.

Verify the signature with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) **v3.0 or newer** (keyless, GitHub Actions OIDC). The signature is stored in cosign v3's bundle format, so cosign v2 reports "no signatures found":

```sh
cosign verify ghcr.io/ncecere/open-mcp-portal@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/open-mcp-portal/.github/workflows/image.yml@refs/tags/v0.1.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The signature covers the multi-arch index, and so every tag that points at it. The SBOM (SPDX) and build provenance are attached to the image as attestations:

```sh
docker buildx imagetools inspect ghcr.io/ncecere/open-mcp-portal@sha256:<digest> --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/ncecere/open-mcp-portal@sha256:<digest> --format '{{ json .Provenance }}'
```

The Release also carries each platform's SBOM as `open-mcp-portal-v0.1.0-linux-<arch>.sbom.spdx.json`, with `checksums.txt` (`sha256sum -c checksums.txt`). `open-mcp-portal version` in the image prints `open-mcp-portal 0.1.0 (<commit>)`.
